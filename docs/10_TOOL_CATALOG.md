# 10 — Tool and command catalog

This is an application interface specification. Provider APIs are documented separately. Schemas from [06](06_DOMAIN_MODEL.md) are canonical. “Tool” does not mean every function is exposed to Gemini.

## Authority boundaries

1. Gemini receives a scoped snapshot and may call read tools.
2. It returns one `ActionProposal`; Pydantic validates its shape.
3. The policy layer checks version, evidence, allowed transition, authorization and outstanding effects.
4. The executor invokes a command; the command owns its database transaction and action/event records.
5. Provider requests happen outside that transaction, using the recorded action identity.

All mutation inputs require authenticated actor context and a caller-supplied idempotency key, supplied by trusted application code, not generated by the LLM. Case-scoped IDs are checked against the authenticated scope. Unknown external results are never treated as failure safe to retry.

## Model-visible read tools

Verified 2026-09-20 against the actual `agent.tool(...)` registrations in
`backend/app/agents/coordinator.py:57-61` and their implementations in
`backend/app/agents/read_tools.py`. Exactly five tools are registered;
this table lists no more and no fewer.

| Name / purpose | Input → return | Side effect | Caller | Failure modes | Human approval |
|---|---|---|---|---|---|
| `read_report` — original contractor evidence | RecordRef → ContractorReport | None | Coordinator | Missing report, wrong case (`ModelRetry`) | No |
| `read_communication` — caller words and normalized outcome | RecordRef → Communication with `recording.media_path` set to null (transcript and `correlation_token_hash` are returned as-is) | None | Coordinator | Missing communication, wrong case (`ModelRetry`) | No |
| `list_case_events` — bounded prior history | ReadEvents → list[CaseEvent] | None | Coordinator | Wrong case (`ModelRetry`); `limit` over 100 rejected by schema validation before the call | No |
| `find_appointment_options` — intersect confirmed windows and connector slots | AppointmentQuery → AppointmentOptions | Reads and, if absent, lazily materializes `MockSlotModel` rows for that contractor/trade (a real write in the tool's own session, not merely a trace) | Coordinator | Unknown work order (`ModelRetry`, self-correcting); empty result with `reason_if_empty` for no matching tenant-availability window or no intersecting slot — these are not errors | No |
| `read_research` — completed contractor-discovery evidence | RecordRef → ContractorSearchResult | None | Coordinator | Missing research snapshot, wrong case (`ModelRetry`) | No |

Correction: an earlier revision of this table listed a `get_case_snapshot`
tool (CaseRef → CaseSnapshot) that does not exist under that name anywhere
in the code, and omitted `read_research`, which is registered
(`coordinator.py:61`). The real API-reuse helper is
`load_case_snapshot(session, case_id)` in
`backend/app/domain/services.py:1510`; it is a plain internal async
function, not a `CaseRef`-typed tool, and it is **not** registered on the
agent (`construct_agent` in `coordinator.py:45-62` registers only the five
tools above). It is called directly by `GET /cases/{case_id}` in
`backend/app/api/cases.py:177` and by the dispatcher in
`backend/app/orchestration/dispatcher.py:152` to build the very snapshot
that becomes the model's prompt. The earlier claim that
`find_appointment_options` performs only a read ("Connector read, trace
only") was also wrong: `MockBookingConnector.list_slots` calls
`_ensure_slots` (`backend/app/integrations/booking.py:36-63`), which
inserts `MockSlotModel` rows the first time a contractor/trade/day
combination is requested. That insert is committed, not just flushed:
`find_appointment_options` reads and writes inside the same
`session_scope()` (`backend/app/db.py:60-69`), which commits on a clean
exit from the `async with` block. A nominally read-only, model-visible
tool therefore does cause a persisted write — worth flagging against
this document's own "Model-visible tools are scoped reads" rule
(CLAUDE.md), even though the write is idempotent and internal (no
provider or case-state effect).

The initial snapshot is already supplied to the model as the run prompt; no read tool re-fetches it. Tools always use `RunContext` to enforce the injected case scope. `get_tenant` and `get_property` are internal reads included in the snapshot, not additional model tools. Do not expose contact secrets or entire unrelated cases.

## Ingress commands, outside the coordinator

| Name / purpose | Input → return | Side effect | Caller | Failure modes | Human approval |
|---|---|---|---|---|---|
| `submit_intake` | IntakeSubmission → case ID, communication ID, CommandResult | Create case/issue or bind existing intake; append CASE_CREATED; enqueue run | Authenticated ElevenLabs tool or demo intake API | Unverified property identity, duplicate, malformed dates | Participant consents to demo call; no repair commitment |
| `record_observations` | ObservationSubmission → CommandResult | Preserve sourced facts; merge validated availability; append INFORMATION_RECEIVED / AVAILABILITY_RECEIVED / TENANT_CONFIRMATION_RECEIVED | Voice tool, normalized post-call adapter, operator | Conflicting facts, ambiguous dates, wrong call token | No for observations; contradictions require review |
| `record_contractor_report` | ReportSubmission → ContractorReport + CommandResult | Save original report; mark AWAITING_REPORT; append CONTRACTOR_REPORT_RECEIVED | Authenticated contractor adapter; simulated demo event control | Wrong contractor/appointment, duplicate external report, contradictory final state | No to record; acceptance may require review |
| `decide_approval` | ApprovalDecision → CommandResult | Bind approval to proposal hash and spend limit; enqueue executor | Operator only | Changed proposal, stale case, insufficient limit | This is the approval action |
| `cancel_appointment` | CancellationRequest + CommandContext → CommandResult | Record cancellation intent, call connector, update only on confirmed cancellation | Operator or verified connector cancellation event | Provider timeout/unknown commitment | Operator initiated in MVP |

Creating an event is a private transaction helper. There is no public `add_case_event` or generic `update_case_details` escape hatch. An actor cannot inject arbitrary lifecycle events.

`propose_next_action` is the model output, not an extra action tool. `rank_contractors` is a deterministic filter: approved trade match → service area → valid slot; tie-break by configured preference. No invented ratings, travel time or availability. Search candidates cannot enter this ranked approved pool without operator verification.

## ContractorConnector boundary

Interface operations: `list_slots(AppointmentQuery) → AppointmentOptions`, `book(BookingRequest) → BookingOutcome`, `cancel(provider_booking_id, idempotency_key) → CancellationOutcome`, `reconcile(action_id, provider_booking_id?) → BookingOutcome | CancellationOutcome`, selected by the recorded action kind.

Implement **MockBookingConnector only** for the hero workflow. It stores slot reservations in the same SQLite database so restart/duplicate tests are meaningful. The mock returns provenance SIMULATED and fictional booking IDs. `HumanDispatchConnector` may simply create a pending operator task. API, email and voice connectors are POST-HACKATHON; their existence as designs is not a claim that contractors expose those interfaces.

Rescheduling is confirmed cancellation followed by a new authorized booking with a new attempt ID. If cancellation is uncertain, do not place a second booking. Email sent, call started and message acknowledged are not booking confirmation.

## Idempotency and errors

Keys encode purpose and target, e.g. `report:{report_id}:prerequisite`, `booking:{work_order_id}:{slot_id}:{attempt}`, `recording:{conversation_id}`. A repeated key with a different payload hash returns CONFLICT. A repeated identical request returns the existing result.

Version checking applies when admitting a fresh proposal. Approving an existing action is not a new model proposal: reload its immutable payload, validate the operator's current case version, recheck all business predicates, store approval and enqueue the same action ID. Revalidate again before send. The approval's own event/version increment must not make that action stale by mechanically comparing its original model snapshot version. Unrelated changed facts can still invalidate its scope/slot/evidence. Provider results for already-sent actions are ingested against the ledger even if case version changed; never discard a real acknowledgment as stale.

Common error codes: VALIDATION_ERROR, NOT_FOUND, FORBIDDEN, STALE_VERSION, POLICY_REJECTED, APPROVAL_REQUIRED, CONFLICT, RATE_LIMITED, PROVIDER_UNAVAILABLE, EXTERNAL_RESULT_UNKNOWN. Read-only transient requests may retry twice with jitter. A potentially committed effect transitions to UNKNOWN and reconciliation, never blind retry. All errors shown to the model are sanitized and bounded.
